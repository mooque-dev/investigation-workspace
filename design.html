Design system & visual rationale

How the deliverables are built — the design system, the component model, and the reasoning behind the visual signifiers and the chosen fidelity.

1.Why a design system here at all

A take-home is judged partly on whether the candidate thinks in systems or in screens. Three surfaces — a high-fidelity editorial overview, a low-fi interactive mock, and a living styleguide — sharing one token + component layer demonstrates the former. It's also just the honest way to keep a multi-file deliverable consistent.

Architecture

ds.css ← tokens + reusable components (the system) ├─ styleguide.html ← living component library (proves reuse) ├─ case-overview.html ← data-theme="editorial" (recruiter-facing) └─ investigation-workspace-mock.html ← data-theme="wireframe" (interactive concept) framing.html ← the product argument design.html ← this file

One stylesheet defines everything once. Both HTML surfaces set a single attribute — data-theme="editorial" or data-theme="wireframe" — and the same markup re-skins itself. The styleguide's "toggle theme" button swaps between them live to prove the components are genuinely shared, not copied.

3.The signifier fix

An earlier review caught two weak signifiers, and the system corrects both:

  • No bare colored bars. A status used to be communicated by a black strip on the alert and an amber strip on the gate — color and position doing the work alone. That fails for a colorblind operator and dies in a grayscale print of a deviation record. The fix: a proper alert component (icon + an "OUT OF BAND" text label + the values) and an icon/dot + text chip for every owner and status. Meaning now survives loss of color.
  • Owner and status are always chips. One .chip primitive, status variants layered on. Because the dot and the text carry the meaning together, the chip reads correctly in any theme and any color condition.
This matters more than usual here: in a regulated setting the artifact gets printed, archived, and read by people who weren't in the room. The signifiers have to be legible out of context.

4.Component model

Everything on every surface composes from a small set of primitives in ds.css:

.chip
The canonical signifier (neutral + danger/warn/ok/info variants). Icon + text + tint = three redundant cues. Never relies on color alone.
.alert
Labeled excursion banner, never a bare bar. Icon, "OUT OF BAND" label, value, and target — all explicit.
.hyp
A ranked hypothesis with a confidence track and for/against evidence. Uses native <details>, so it's keyboard-accessible and works without JS.
.ladder
The autonomy/investigation plan with done / running / gated states. Status lives in the marker icon + chip, never an edge color.
.note
Pinned designer reasoning (dashed accent border), so the "why" travels with the artifact instead of in a separate deck.
.btn, .card
The structural workhorses — consistent affordances everywhere.

Spacing, type scale, radii, and status hues are all tokens, so the wireframe can square off radii and flatten shadows by overriding a handful of variables rather than rewriting components.

5.Why the mock is deliberately low-fidelity

This is a real position, not a shortcut. For a founding/staff role the question being tested is judgment under ambiguity, not visual polish — the brief says outright it cares more about decision-making, product thinking, and interaction design. High-fidelity screens at this stage would invite feedback on the wrong layer (color, spacing, iconography) and quietly imply the hard decisions are settled when they aren't.

So the mock wears its fidelity on its sleeve: monospace type, a grid-paper backdrop, hairline borders. It is interactive where interactivity carries an argument — you can expand a hypothesis to see evidence both ways, and the approval gate genuinely refuses to enable until you type a rationale, because that constraint is the design point. Everywhere else it stays a sketch.

The reasoning is pinned directly onto each of the three directions via .note blocks, so a reviewer reads the why next to the what without a companion deck.

6.Accessibility & honesty notes

  • Hypotheses use native <details>/<summary> — keyboard-operable and functional with JS disabled.
  • Status is never color-only; every chip pairs a dot/icon with text.
  • The guided tour is fully skippable and Escape-dismissable; arrow keys and Enter advance it.
  • The mock is a front-end concept, not a working system: there's no real control-system integration, and the data is illustrative. That boundary is stated rather than hidden — which is itself the posture the product takes toward its own users.
